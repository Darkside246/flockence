## First implementation slice

Flockence stores a versioned snapshot assessment on the existing health observation and links it to the existing private photo. It records the configured model, acquisition source, inspection focus, visible findings, evidence and checks. Each category starts as unobserved. A warning or critical finding stays visible when other categories lack evidence. Results are model observations for human review. There is no numerical risk score in this slice.

The historical comparison endpoint uses the signed-in farm. It requires two versioned assessments with the same recorded camera name and provider, model, inspection focus and batch. It compares categories with evidence in both records. Recorded names are all the current worker contract supplies. A stable camera identity, fixed in the camera-to-pen assignment, is required before treating camera replacement or relocation as longitudinally equivalent. Existing observations remain readable. Older entries have no structured categories to compare.

The nullable `HealthObservation.visionAssessment` field inherits existing PostgreSQL row security. Follow the [production database baseline procedure](./PRODUCTION_DATABASE_MIGRATION_BASELINE.md). Review and apply `ops/postgres/add-vision-assessment.sql` against a restored staging database before attempting a deployment. Verify row grants, older observations, signed-in camera capture, report export and both sides of any future Oriya change. The CI schema push is only for a disposable database.

## Controlled implementation order

| Phase | Deliverable | Completion evidence |
| --- | --- | --- |
| 1. Source and architecture review | This matrix, camera and data boundaries, known blockers | Review the missing ChickenOp summary and verify live service revisions before claiming live coverage |
| 2. Assessment foundation | Versioned evidence and matched snapshot comparison first, then stable camera and pen assignment, reviewed labels and model registry | Cross-farm role tests, authorized writes, repeatable retrieval, migration rehearsal and human review of representative footage |
| 3. Live video | Sampling through private camera workers, device health, isolated inference, frame quality, per-view detection, tracking and activity summaries | Held-out farm evaluation, count error, precision, recall, F1, false alarms, tracking ID switches, lighting and occlusion results |
| 4. Environmental evidence | Normalize timestamp, units, sensor location, freshness and device quality. Pilot MQTT and supported RS485 gateways before wider rollout | Verified timestamps, missed readings, power and sensor state, replay and outage handling |
| 5. Oriya tools | Read-only condition, history, camera status, environmental readings and alerts first. Add snapshot requests, reports and task creation with explicit bounded permissions | Signed contract tests, per-tool entitlement and usage, cross-tenant rejection, task audit with human approval and replay checks |
| 6. Forecasts | Recorded batch benchmarks, growth and FCR first. Add feed, water, cost and profit projections after cohort validation | At-age comparisons, out-of-time validation and documented assumptions and uncertainty |
| 7. Release | Mobile entry and offline retries, performance and retention, alert deduplication, recovery and deployment | Authorized VPS staging smoke tests, database restore rehearsal, live device validation and verified plan boundaries |

A future scoring model needs reviewed reference data by age, strain, housing, stocking density and production type. Build camera and sensor trust separately before joining observations. Keep evidence, model estimates and recommendations distinct. Avoid sending continuous feeds to a language model or inferring ammonia, humidity, water quality or disease from images. Any private footage used beyond the original inspection requires explicit permission and a review workflow.
